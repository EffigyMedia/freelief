### AUD-008 - A failed data load on a deep link to Standards stops the router, and from another screen it leaves a frozen copy of the previous screen

- Severity: Medium
- Area: C. Error handling
- Evidence: Quoted this round (UNT-010). app.js boot runs `await show(routeName(), { moveFocus: false }); window.addEventListener("hashchange", ...)`, so the hashchange listener is added only after the first screen starts. screens/standards.js does `await Promise.all([fetch("data/standards.json").then((r) => r.json()), ...])` with no catch. app.js show() calls "current.stop()" on the previous screen and then awaits "current.start(main, ...)"; the stopped screen's DOM stays in main until the start resolves, and if the start rejects, the hashchange handler gets an unhandled rejection. Scratch probe with data/standards.json aborted: opening `#standards` then setting `location.hash = '#breathe'` -> 'guide: 0 | screen: standards' (navigation is dead). Opening from the breathing screen then going to `#standards` -> 'shown: None | guide still: 1 | nav: #menu': the breathing guide was stopped but its DOM stays on screen, frozen, under the Standards route. (quoted in round UNT-010)
- Impact: A person who opens a shared link to the Standards page on a bad connection cannot reach the breathing guide or any other screen without a reload. A failed load from the menu shows a still breathing circle that no longer breathes, with controls that do nothing and no message. Both break the design's 'any failure leaves the breath guide usable'.
- Direction: Register the hashchange listener before the first `show`. In `show`, clear `main` or show a calm loading line before an async start, catch a rejected `start`, and render a calm error line from strings that says what still works, with a link back to `#breathe`. Give standards.js a `response.ok` check and a catch. Add a test that aborts standards.json on a deep link and then navigates to `#breathe`.
- Effort: S
