### AUD-006 - The Feedback page does not tell the person that a GitHub issue is public

- Severity: Medium
- Area: E. Privacy & licensing
- Evidence: strings/en.json: `"feedback.githubNote": "Opens GitHub in your browser with this message filled in. GitHub needs a free account."` and `"feedback.intro": "... Nothing is sent by Freelief itself: you read and edit the message, then send it yourself."`. Neither string says the issue is public. feedback.template.problem has no warning. The warning exists only as an HTML comment in `.github/ISSUE_TEMPLATE/problem-report.md`: `Please do not include personal health details. This page is public.` `accessibility-check.md` has no warning. `screens/feedback.js` sets `issue.searchParams.set("body", message.value)`. Per GitHub's documented behaviour (not run here), a supplied body replaces the template body, so the person never sees that comment. Design F9 and REQ-030 make the issue the primary feedback route. The design also treats feedback personal data as never-commit material. (quoted in round UNT-010)
- Impact: The users are people in or near a panic attack, and some are volunteers with disabilities. One could describe their mental-health history in a public issue tied to their GitHub identity, in the belief that it goes privately to the maintainers. Once indexed, it cannot be recalled. This works against the product's 'ask nothing, keep nothing' stance.
- Direction: Add a plain line beside "Open on GitHub", and at the top of both pre-filled texts, that says a GitHub issue is public and that health or personal details should not go in it. Add the same warning to `accessibility-check.md`. Add a test that asserts the warning shows on the Feedback page and is linked by aria-describedby to the GitHub control.
