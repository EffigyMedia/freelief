### AUD-087 - bench's response probe stops at the next requestAnimationFrame, before the dialog's frame is rendered, so it does not measure the 'visible' response REQ-027 names

- Severity: Low
- Area: D. Performance
- Evidence: tools/bench.py RESPONSE_PROBE (quoted in round UNT-082): `requestAnimationFrame(() => resolve(performance.now() - start))`. rAF callbacks run at the start of the rendering update, before that frame's style, layout and paint. baseline.md calls the metric 'from a click on Need urgent help? to the next frame after the dialog opens', and REQ-027 says 'a visible response within 100 milliseconds'. Scratch probe, same setup as bench (installed, offline, CPU 4x, 7 runs), adding a MessageChannel message posted from inside that rAF: median 78.2 ms at the rAF and 84.6 ms after the frame. Runs [77, 78, 78, 80, 102, 78, 74] against [83, 85, 85, 86, 111, 84, 80]. (quoted in round UNT-082)
- Impact: The figure understates the visible response by about 6 ms (8%) on this machine. That matters only near the 100 ms target, where the worst runs already sit (102.7 and 111 ms). The baseline and the target are compared on an end point earlier than the one the requirement names.
- Direction: End the probe after the frame is rendered: requestAnimationFrame, then a MessageChannel message or setTimeout(0). Re-baseline the response figure with a log note that says the end point changed.
- Effort: S
- Found by: the operations lens of round [[UNT-082]].
