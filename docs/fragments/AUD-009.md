### AUD-009 - The update test that the design names as the mitigation for a stale offline cache does not exist

- Severity: Medium
- Area: H. Test coverage
- Evidence: Quoted this round (UNT-010). Design section 8, hard problem 1: "Offline install and update. Proven first, in the walking skeleton, with an offline test and an update test." Section 9 tests: "Update: a new cache version replaces the old one." Risk table (section 11): "The offline cache serves an old version after an update. | The cache name carries the version; an update test covers it." A grep of tools/tests for update, activate, caches., cache name and freelief- finds no such test; test_offline.py holds only test_cache_list_matches_the_shipped_files, test_the_app_works_offline_after_one_visit and test_the_manifest_makes_the_app_installable. Neither changes the version or checks that the old cache is deleted. A search of *.md and *.py for "update test" or "test_update" finds only the design document. The harness also sets `Cache-Control: no-store` on every response, so the suite never meets the production condition (GitHub Pages sends `Cache-Control: max-age=600`, read with curl -sI this round). (quoted in round UNT-010)
- Impact: The path every installed user takes on each release (new worker installs, old cache is deleted, new files served offline) has never run in a test. The risk table tells readers this risk is mitigated when it is not, so a broken update would ship unnoticed and strand installed users on an old or empty cache, with old crisis lines.
- Direction: Add a browser test that installs the app, serves a changed version.js and one changed file (via route or a temporary copy served by the harness), triggers `registration.update()` or reloads until the new worker controls the page, then asserts `caches.keys()` equals ['freelief-<new>'] and that an offline reload shows the changed file and the page reports the new version. Until the test exists, correct the Stage 11 risk-table mitigation text.
- Effort: M
