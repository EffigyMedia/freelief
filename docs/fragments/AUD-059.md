### AUD-059 - The worker's fetch handler has no catch, so a Cache Storage error answers every request with a network error, even online

- Severity: Low
- Area: C. Error handling
- Evidence: Quoted in this round. sw.js: `event.respondWith(caches.open(CACHE).then((cache) => cache.match(event.request, { ignoreSearch: true })).then((cached) => { if (cached) return cached; return fetch(event.request)...` with no `.catch`. If caches.open or cache.match rejects, respondWith gets a rejected promise and the browser returns a network error; the request is never sent to the network. Confidence: from reading the code; a rejecting Cache Storage was not reproduced this round. (quoted in round UNT-051)
- Impact: On a device where Cache Storage fails (storage pressure, a corrupted store), every request from the installed app fails, including online, so the app cannot start until its site data is cleared. The page fallback in index.html cannot help, because index.html itself is a request through this handler.
- Direction: Add `.catch(() => fetch(event.request))` after the cache lookup, so a cache fault degrades to the network. Add a unit-level test that stubs caches.open to reject inside the worker, or at least a source assertion.
- Effort: S
- Found by: the operations lens of round [[UNT-051]].
