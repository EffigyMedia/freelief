### AUD-186 - show() calls the old screen's stop() with no guard, so a stop() that throws leaves the person on the old screen with the address already changed

- Severity: Low
- Area: C. Error handling
- Evidence: Round UNT-155. app.js show() starts with `if (current) current.stop(); current = null;`, with no try/catch. The hashchange listener calls `show(routeName(), { moveFocus: true })` and does not handle the promise it returns. The AUD-165 fix guards stop() only on the start-failure path: `try { screen.stop?.(); } catch (stopError) { console.error(...) }`. Confidence: low. This round found no screen whose stop() throws today. Every stop() it read is small: breathe.js clears timers, cancels a frame, stops a tone and releases the wake lock. (quoted in round UNT-155)
- Impact: If a future screen's stop() throws, every link away from that screen fails silently, apart from an unhandled rejection in the console. The hash changes, but the old screen stays and nothing new loads. 'Need urgent help?' still works, because it is a dialog. Reaching the menu then needs a reload, and a person in a crisis may not think of that.
- Direction: Guard the stop() at the top of show() in the same way as the AUD-165 path: `try { current?.stop(); } catch (error) { console.error(...); }`. Extend test_startup.py with a stub screen whose stop() throws, and assert that a link away from it still shows the menu.
- Effort: S
