### AUD-166 - Coming back to the app before the first touch creates the AudioContext without a gesture, against audio.js's own rule

- Severity: Low
- Area: C. Edge cases
- Evidence: Quoted in round UNT-139. audio.js: 'Until then nothing is created, so no "AudioContext was not allowed to start" warning appears; the first gesture anywhere in the app unlocks sound'. app.js boot: `document.addEventListener("visibilitychange", ...) else if (getSetting("sounds") && !helpOpen) { audio.applySound(true); background.restart(); }`. `applySound(true)` calls `unlockAudio()`, which sets `unlocked = true; ensureContext();` with no gesture. (quoted in round UNT-139)
- Impact: A person who opens Freelief (for example with 'Start breathing at once') and switches away and back before touching it gets an AudioContext created outside a gesture. Chrome prints the warning that the comment promises never appears. `canPlay()` is then true while the context is suspended, so breathing cues are scheduled on a frozen clock. The first touch recovers the audio, so the harm is a console error and a false invariant.
- Direction: In applySound(true), resume only if `unlocked` is already true. Do not call unlockAudio() from a non-gesture path. Keep unlockAudio() for the speaker button and the sound bar. Add a test: hide and show the page before any input, then assert a clean console and no AudioContext.
- Effort: S
- Found by: the operations lens of round [[UNT-139]].
- **RULED 2026-10-10T19:50:16-04:00** — 2026-10-10 (UNT-152, v0.8.32): fixed; in-flight. applySound(true) creates or resumes the audio only when a gesture has unlocked it (the initAudio listener); unlockAudio(), now unused, is removed. test_coming_back_before_any_touch_creates_no_audio hides and shows the page before any input and finds no AudioContext and a clean console; it failed against the old audio.js.
