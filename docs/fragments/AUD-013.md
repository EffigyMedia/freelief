### AUD-013 - The worker's precache fills a new versioned cache through the browser HTTP cache, so a new version can freeze old files

- Severity: Medium
- Area: C. Edge cases
- Evidence: Quoted this round (UNT-010). sw.js install: "event.waitUntil(caches.open(CACHE).then((cache) => cache.addAll(FILES)).then(() => self.skipWaiting()));". No Request carries {cache: "reload"}, so the requests use the default cache mode and the browser HTTP cache may answer them. `curl -sI` on https://effigymedia.github.io/freelief/app.js and /data/crisis-lines.json returned `Cache-Control: max-age=600`. The test harness sends "Cache-Control", "no-store" ("Never let the test server's own caching hide a stale file"), so the tests cannot see this. Confidence: the mechanism is documented browser behaviour and the header is confirmed, but the stale-store case was not reproduced in this round. (quoted in round UNT-010)
- Impact: For up to 10 minutes after a deploy (for example a quick fix after a phone-test push), a browser that already holds old files in its HTTP cache can store them under the new cache name. That mixed build is then served offline until the next version, and it can include old app.js or old crisis-line data.
- Direction: Precache with `cache.addAll(FILES.map((f) => new Request(f, { cache: "reload" })))`, and consider adding the version as a query string on precache requests (the fetch handler already uses ignoreSearch). Cover this in the update test with a server that sends max-age, not no-store.
- Effort: S
- Found by: the operations and omission lenses of round [[UNT-010]] - convergence.
- **RULED 2026-10-07T14:38:29-04:00** — Attempt 1, UNT-011 (v0.5.1): precache and the heal repair fetch every file with new Request(file, { cache: 'reload' }), past the HTTP cache. A source assertion covers it; the version-query idea in the direction was not taken, because cache 'reload' already bypasses the HTTP cache. A later round confirms.
