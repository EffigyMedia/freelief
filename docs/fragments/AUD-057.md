### AUD-057 - After a touch, a mid-session update serves the new version's lazy screens to the old shell, and a screen that cannot load bounces to the menu and leaves its own link dead

- Severity: Medium
- Area: C. Regression risks
- Evidence: Quoted in this round. app.js: 'Once they have touched or typed, never interrupt them: the new version then applies at the next open.' But sw.js calls `self.skipWaiting()` and `self.clients.claim()`, and the fetch handler answers from the NEW `caches.open(CACHE)`, so `import("./activities/ripple.js")` in the old page gets the new file while settings.js, strings and config stay old. show(): on a failed import `if (name !== DEFAULT_ROUTE) return show(DEFAULT_ROUTE, { moveFocus });`, which leaves location.hash unchanged. Scratch probe: install, click the page, deploy a next version where settings.js gains an export and ripple.js imports it, run registration.update(), set `#ripple` -> `{'screen': 'menu', 'shown': 'menu', 'hash': '#ripple'}`, console: "Freelief could not load the ripple screen: SyntaxError: The requested module '../settings.js' does not provide an export named 'addedInNextVersion'". The page still reported version 0.5.36. (quoted in round UNT-051)
- Impact: This project ships many versions a day (v0.5.0 to v0.5.36 on 2026-10-07). A person who opens the app, taps once, and then picks an activity after an update arrives can get an activity that silently will not open, or one built with a new string key that the old string table does not hold (t() then shows the raw key). Because the hash stays on the failed route, tapping the same menu item again fires no hashchange and does nothing, so the activity is unreachable until a reload. The comment tells the next maintainer that this cannot happen.
- Direction: Pick one rule and make the code and comment agree. Either (a) do not call skipWaiting/clients.claim while a client is open after interaction, and let the new worker wait until the next open, or (b) keep the old version's cache until no old client remains and answer each client from the cache of the version it loaded (for example with the version as a query on module URLs). In show(), when a screen falls back, `history.replaceState` the hash to the route actually shown, so its menu link works again. Add a test that interacts, deploys a version with a changed lazy module, and opens that screen.
- Effort: M
- Found by: the operations lens of round [[UNT-051]].
- **RULED 2026-10-08T02:05:45-04:00** — Fixed in UNT-057 as v0.5.42, by rule (a). sw.js install no longer calls skipWaiting; it skips only on a 'skip' message. app.js posts 'skip' to a waiting or newly installed worker only if the page had a controller and has not been touched; Update now posts it after the person asks. show() replaces the hash with #menu when a screen falls back. Tests: after a touch an update waits, the page keeps its version and loads the Visualizer-era mandala screen from its own cache, and a new page gets 9.9.7; a deleted ripple.js falls back with #menu. Both fail against the old sw.js and app.js. The earlier update tests still pass. Technical reference updated. 123 tests.
- **Re-checked 2026-10-08T17:06:27-04:00 by round [[UNT-082]]:** found not fully fixed.
  - the operations lens: partly done - AUD-057 is marked built, but its fix holds only when one page is open. app.js: `const offerTakeover = (worker) => { if (worker && hadController && !interacted) worker.postMessage("skip"); };`. Here `interacted` is the flag of the page that sends the message, and no other page is consulted. sw.js: `if (event.data === "skip") { self.skipWaiting(); return; }` and activate does `.then(() => self.clients.claim())`. Scratch probe in round UNT-082 (a copy of the app served by harness.serve): page A installs the app and is touched, version.js goes to 9.9.7 and mandala.js is broken in the same way as the AUD-057 test, the update waits, and then page B opens fresh. Result: 'A version still 0.6.16', 'caches: ['freelief-9.9.7']', and after `location.hash = 'mandala'` page A shows 'A shown: menu hash: #menu parts: 0'. The old cache is deleted under a touched page, and that page then loads the new version's lazy screen. The hash fix in show() works: the address became #menu. The test test_after_a_touch_a_new_version_waits_and_the_session_keeps_its_own_files closes page A before the 'next open' page, so it never covers a second window. Direction (a) of the finding said: 'do not call skipWaiting/clients.claim while a client is open after interaction'. Not met when a second window, such as the installed app plus a browser tab, opens.
