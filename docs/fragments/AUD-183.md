### AUD-183 - build --release accepts a logged bench run that missed a target, so the release gate proves a valid run exists, not that REQ-026, REQ-027 and REQ-028 were met

- Severity: Medium
- Area: D. Performance
- Evidence: Round UNT-155. tools/freelief.py valid_bench_logged(): `if f"(v{version})" in heading and "NOT VALID" not in heading and "Response: Need urgent help?" in entry: return True`. Nothing reads the Verdict column. bench.py write_log_draft() marks a heading only for load: `state = "" if valid else ", NOT VALID: busy machine"`. A valid run that exits 1 for a missed target therefore writes a heading the gate accepts. Probe: `freelief.valid_bench_logged('0.8.14')` returned True. That log entry reads '| Response: Need urgent help? opens (to after paint) | 77 ms | 100.1 to 102.9 ms | +30% to +34% | FAIL (AUD-131) |', and the round recorded that none of its runs is comparable under the current 32% limit. (quoted in round UNT-155)
- Impact: A release can pass build --release with the urgent-help response over its 100 ms target (REQ-027), as long as the log entry names the version. The gate the owner ruled for AUD-159 then looks green for a version that failed the benchmark, and only a person reading the table would see it. It does not hurt users today: v0.8.32's valid run passed every target.
- Direction: Have valid_bench_logged also require that no row's Verdict is FAIL. Better, have bench write output/bench.json with the version, the commit, the validity and each verdict, and have build --release read that record or a copy committed to docs/performance. Then the check does not depend on a hand-copied heading. Add test_repo cases for a valid entry with a FAIL row and for an entry over the current load limit.
- Effort: S
