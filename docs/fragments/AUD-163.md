### AUD-163 - Update now's refresh stores network files without checking that the network still serves this version

- Severity: Low
- Area: C. Edge cases
- Evidence: Quoted in round UNT-139. sw.js: the 'refresh' branch runs `fresh.addAll(FILES.map((file) => new Request(file, { cache: "reload" })))` and then `cache.put(request, response)` into `caches.open(CACHE)`, with no call to `thisVersionIsDeployed()`. The heal and fetch-through paths both call it, and their comment says: 'A file is stored in this version's cache only while the network still serves this version, so one cache never holds two versions (AUD-120).' (quoted in round UNT-139)
- Impact: Suppose a deploy lands between `registration.update()` and the refresh fetches, or a CDN edge serves the new files before the new sw.js. The cache named for the running version then holds a newer version's files, including version.js. This is the mixed state that AUD-120 closed for the other two paths. The window is short, so the risk is low.
- Direction: Before the copy, require `thisVersionIsDeployed()` (or compare the fetched version.js with self.FREELIEF_VERSION), and reply `refresh: false` when it does not match. Add a case to test_a_newer_deploy_is_never_stored_in_the_running_versions_cache that posts 'refresh' after `_deploy(app, "9.9.8")`.
- Effort: S
- Found by: the operations lens of round [[UNT-139]].
- **RULED 2026-10-10T19:40:00-04:00** — 2026-10-10 (UNT-151, v0.8.31): fixed; in-flight. The refresh handler first requires thisVersionIsDeployed(); on a mismatch it stores nothing and replies { refresh: false }. test_a_newer_deploy_is_never_stored_in_the_running_versions_cache now posts 'refresh' after the 9.9.8 deploy and expects false and no stored file; it failed against the old sw.js.
