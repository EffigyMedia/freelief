### AUD-131 - The urgent-help response (REQ-027) misses its 100 ms target on every valid bench run of v0.8.14

- Severity: High
- Area: D. Performance
- Evidence: Quoted in this round from the health step. 'python tools/freelief.py bench' had four valid runs at 33.1% to 34.9% load, and each one exited 1 with '[FAIL] Input to visible response (REQ-027)' at 102.9, 101.5, 101.2 and 100.1 ms. The target is 100 ms and the baseline is 77 ms (+30% to +34%). The worst response was 108.5 to 117.1 ms. docs/performance/baseline.md gives the tolerance as '+25%, and never over 100 ms' and warns: 'The urgent-help response is close to its target: a 35% rise would cross it, so watch it.' My own run this round was refused as busy ('[BUSY] the CPU load reached 67.8%'), and it measured '115.4 ms (target 100 ms; baseline 77 ms, +50%)'. Since the v0.7.13 baseline (commit e695bfb), 25 shipped files have changed, and the help-open handler now also calls 'background.hold()' (AUD-113). The header moved to three rows (v0.8.2). (quoted in round UNT-124)
- Impact: The probe measures the never-break control, 'Need urgent help?' opening, on the phone stand-in. A person in crisis waits longer than the design allows for the crisis lines. Bench exits 1, so a release of this tree cannot pass the Release row's validate step. Some of the rise may come from machine load (see the bench-validity finding), so the true size of the regression is not known.
- Direction: First run bench on a quiet machine at the baseline's load (22% to 27%) to measure the true figure. If the response is still over 77 ms + 25%, profile the click-to-paint path in DevTools with 4x CPU throttling. Look at the style recalculation caused by adding 'help-is-open' to the root element, at background.hold() and audio.applySound(false) running before showModal(), and at the new three-row header. Move any work that a person does not need to see to after the dialog paints. Record the result in docs/performance/log.md.
