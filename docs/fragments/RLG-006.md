### RLG-006 — Launch time regressed to about 224 ms (baseline 110 ms, tolerance +25%): load the non-breathing screens lazily
- **RULED 2026-10-07T19:56:55-04:00** — Source: perf checkpoint, UNT-018, v0.5.6. bench (offline, CPU 4x slower, median of 7) gave 231 ms and then 224 ms to the freelief-ready mark, against the 110 ms baseline and its +25% tolerance. The 1 s target (REQ-026) still holds. Cause, by reading: app.js imports every screen statically, and each new screen (sounds, shapes, Calm) adds to what the browser parses before the breathing guide draws. Direction, already planned in docs/performance/log.md: import the non-breathing screens with dynamic import() on first visit, keeping breathing, the shell and urgent help in the first load.
- **RULED 2026-10-07T20:04:07-04:00** — Built in UNT-019 (v0.5.7). Profiling on a scratch copy showed that the screen modules were not the main cost: lazy loading alone gave 224 -> 214 ms. The static fallback from AUD-002 was: the browser laid out and painted it before running the app (boot started at about 161 ms; about 70 ms without the fallback). fallback.js, a classic script in <head>, now hides the fallback before the first paint and shows it again if the app is not ready within 2 s; app.js shows it at once on a failed boot; with JavaScript off it shows as before. The non-breathing screens also load on first visit. bench: 132 ms launch (baseline 110 ms, +20%, within tolerance), 10 ms response, 122 KB.
- **RULED 2026-10-07T20:05:44-04:00** — Correction, same unit: a second bench run on v0.5.7 gave 146 ms (+33%), just over the +25% tolerance; the first gave 132 ms. The performance log records the range as borderline, far inside the 1 s target, to be watched at the next checkpoint.
