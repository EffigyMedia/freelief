### AUD-121 - The Incident rollback names 'the previous release tag', but the repository has no tag, so the public preview has no named rollback target, and the rule says nothing about Settings that a newer version wrote

- Severity: Low
- Area: H. Build and deployment readiness (rollback); G. Missing documentation
- Evidence: Quoted in round UNT-104. AGENTS.md Incident row: 'The owner may move `live` back to the previous release tag at once, with no round: `git push --force origin vPREVIOUS:live`.' The design repeats this in section 7 row 7: 'Rollback moves `live` back to the previous release tag'. `git tag` printed nothing and `git ls-remote --tags origin` returned nothing. The public preview has moved five times (changelog: 0.6.0, 0.6.3, 0.6.15, 0.7.0, 0.7.3), and each move is recorded by version, not by commit. origin/live is f26bcff ('Record the move of the live preview to v0.7.3'), and its version.js is "0.7.3". That version is public now. A local branch `live` still points at 75e923f (v0.5.0, the colour sort), and nothing updates or removes it. settings.js `save()` writes only `chosen`, which is built from the running version's validators. The v0.7.3 validators (origin/live) have no natureSound or awakeMinutes, so a rollback drops those choices at the next save. (quoted in round UNT-104)
- Impact: Before 1.0, a wrong crisis number or a broken start-up in the public preview has no stated rollback target. An owner who follows the row in a hurry finds no vPREVIOUS, and a hurried `git push --force origin live` would deploy v0.5.0. The first release after 1.0 also has no earlier tag to roll back to. After any rollback, a person's newer settings are lost at their next change. Low confidence on reach: no rollback has happened yet.
- Direction: Tag every live move, for example with a preview tag (preview-0.7.3) on each 'Record the move of the live preview' commit. Alternatively, state in the Incident row and the design that before 1.0 the target is the commit named in the previous move record (record its commit in the changelog entry), and name the command. Delete the stale local `live` branch or document it. Add one sentence to the Incident rule on Settings: either keep keys that the running version does not know when saving, or accept the loss in words. Add an Instruction Changelog entry.
