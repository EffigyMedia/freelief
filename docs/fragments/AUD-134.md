### AUD-134 - Bench accepts runs at up to 35% CPU load against a baseline taken at 22% to 27%, so a valid run cannot separate a regression from machine load

- Severity: Medium
- Area: D. Performance
- Evidence: Quoted in this round. tools/bench.py: 'BUSY_LOAD_PERCENT = 35' and 'TIMING_TOLERANCE = 0.25'. docs/performance/baseline.md: 'the re-baseline below used runs at 22% to 27% load'. log.md (v0.7.13): 'Runs at 22.2%, 26.6% and 25.9% busiest load gave 79.7, 77.6 and 76.8 ms'. In the health step, valid runs at 33.1% to 34.9% load measured 100.1 to 102.9 ms, and two runs (40.5% and 55.2%) were refused. My run at 67.8% measured 115.4 ms. The response rises with load by an amount near the +25% tolerance and the 23 ms of headroom. The baseline's own load is not compared with the load of a run. (quoted in round UNT-124)
- Impact: The figure that gates a release depends on what else the machine is doing. A real regression can hide under a quiet run, and load alone can fail a run on clean code. The Release row's validate step ('run bench on a quiet machine') then has no fixed meaning. This is the 'passes only under special conditions' case that Audit_and_Testing.md section 5 step 3 names.
- Direction: Record the baseline's load next to its figures in baseline.md. Have bench refuse, or mark as not comparable, a run whose busiest load exceeds the baseline's load by more than a small margin, for example 5 points. Or lower BUSY_LOAD_PERCENT to near the baseline's load. Print both loads in the result. Consider more runs, or a trimmed mean, for the response, which has a spread of up to 17 ms.
